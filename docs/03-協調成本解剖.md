# 03｜協調成本解剖：平行處理的收益去哪了？

那則 X 貼文的技術核心只有一句：**平行化不會增加你的預算，只會增加你的開銷**。本頁把「開銷」拆開算給你看。

## 3.1 四種協調成本

### ① Token 成本（最直接）

| 形態 | 相對 token 消耗（Anthropic 生產數據） |
|---|---|
| 一般聊天 | 1× |
| 單一 agent | ~4× |
| **多代理系統** | **~15×** |

多出來的部分不是「額外的工作」，而是：任務描述、狀態回報、中間結果轉述、匯總與重試。**如果分支的輸出本身不大、但要靠大量對話才能交接，交接成本可能大於工作本身。**

速算式：

```
多代理總成本 ≈ Σ(各 agent 獨立工作 token) + 交接 token × 分支數²
                          ↑ 實際收益來自這裡      ↑ 協調稅，隨分支數快速長大
```

### ② Rate limit / 用量上限（貼文嘲諷的重點）

所有 agent 共享同一份訂閱額度：

- 200 個 agent **不是** 200 倍算力，而是同一條水管被切成 200 股；
- 瓶頸從「單 agent 想不完」變成「集體排隊等額度」；
- 平均回應延遲上升，長尾更糟（一個分支撞限流，匯總端全體等待）。

**判準**：如果你的系統是 quota-bound（受固定額度限制）而非 latency-bound（受思考時間限制），增加 agent 數通常只會把等待從「串行」變成「擁塞」。

### ③ 上下文割裂（Cognition 論點）

- subagent 看不到彼此的決策與脈絡，只能透過「任務描述」這條窄管溝通；
- 任務描述寫得含糊 → 重複工作、漏東漏西（Anthropic 實測：光是把委派指令寫具體，就消除了 subagent 之間的重複搜尋）；
- 最終匯總時，主 agent 只拿到**被壓縮過兩次**的結論，原始脈絡已丟失。

### ④ 同步與驗證成本

- **同步瓶頸**：Anthropic 的 lead agent 同步等待每批 subagent，一個慢分支拖住全隊；
- **驗證責任轉移**：單代理出錯是「一條軌跡」，多代理出錯要先分辨「哪個分支錯了」——MAST 的 14 種失敗模式多半出在這裡；
- **重試乘數**：分支失敗 → 匯總發現缺漏 → 重開分支，成本非線性放大。

## 3.2 收益什麼時候蓋過成本？

平行收益成立需要**同時**滿足（缺一就容易翻車）：

1. **分支真正獨立**：分支之間不需要即時交換狀態；
2. **分支數量 × 單分支工作量 > 交接成本**：小任務開分支是負資產；
3. **匯總便宜**：把 N 份結論合成 1 份，比重新做一遍便宜得多；
4. **資料量超過單一 context**：多個 context window 是為了「裝更多」，不是為了「更聰明」；
5. **任務價值付得起 10–15× token**：Anthropic 的原話是「economic viability」——只有任務夠值錢，多代理才划得來。

## 3.3 一張圖的心智模型

```
單代理：  [思考→行動→思考→行動]......→ 結果
          成本 = 工作本身；瓶頸 = 速度（序列）

多代理：  [主管 分派]
            ├─ [agent A 獨立工作] ─┐
            ├─ [agent B 獨立工作] ─┼─ [匯總] → 結果
            └─ [agent C 獨立工作] ─┘
          成本 = 工作本身 + 分派 + 交接 + 匯總 + 排隊
          瓶頸 = 匯總端 + 共享額度

→ 當「分支獨立且夠肥」，成本差距被時間/覆蓋率補回來；
→ 當「分支互相依賴或很瘦」，協調稅直接吃掉全部收益。
```

## 3.4 對應到 X 貼文

- 「200 agents competing for [usage limits]」= ②；
- 「burning tokens coordinating with each other」= ① 的交接 token + ④；
- 「couldn't have been done just as effectively by a single agent」= 本頁 3.2 的五個條件——**作者要的是同時滿足五個條件的案例，目前討論串還沒有人交出可量測的版本**。
