# 04｜決策框架：五問評分表（附 Discord 任務分派應用）

討論串吵不出結果的主因，是雙方都沒有共同的判準。這份評分表把 `03-協調成本解剖.md` 的五個條件變成可操作的工具。

## 4.1 五問評分表

每題 0–2 分（0＝不成立，1＝部分成立，2＝完全成立），滿分 10。

| # | 問題 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|---|
| **Q1 分支獨立性** | 各分支需要即時共享狀態嗎？ | 分支必須同步協作 | 偶爾需要查共享狀態 | 分支完全可獨立執行 |
| **Q2 可驗收性** | 分支輸出能被獨立檢查、低成本匯總嗎？ | 無法判斷分支對錯 | 可判斷但要人工審 | 可自動驗收、匯總很便宜 |
| **Q3 Context 壓力** | 任務資料量會撐爆單一上下文嗎？ | 單一 context 綽綽有餘 | 接近上限 | 明確超過，必須分載 |
| **Q4 任務價值** | 產出價值付得起 10–15× token 嗎？ | 低價值、日常例行 | 中等價值 | 高價值、可計價 |
| **Q5 共享瓶頸** | 是否受共享 rate limit / 單一狀態源節制？ | 強共享瓶頸（如單一 DB 鎖） | 部分共享 | 無瓶頸、可水平擴充 |

### 分數 → 建議架構

| 總分 | 建議 | 說明 |
|---|---|---|
| **0–3** | **單代理 + 工具/工作流** | 用 deterministic workflow（Anthropic 的「building effective agents」原則：先用最簡單的形狀） |
| **4–6** | **單代理為主，抽查式平行**（best-of-n） | 同題平行取樣、投票匯總；不做任務分工，規避交接成本 |
| **7–8** | **主管–工人（2–4 agents）** | 僅在 Q1、Q2 都拿滿分時啟用；分支數從小開始（Anthropic：簡單查詢 1 agent/3–10 tool calls，一般比較 2–4 subagents） |
| **9–10** | **平行扇出（≥5 agents）** | 只有 Q3 也拿滿分（context 真的裝不下）時才考慮；先驗證匯總端不會成為瓶頸 |

### 兩條硬性否決（一票否決）

- ❌ **Q1 = 0**：分支必須同步協作 → 無論分數多高都不要開代理群（對應 Nature 2026 的 PlanCraft：−39% ~ −70%）。
- ❌ **Q5 = 0 且 Q4 ≤ 1**：共享瓶頸強 + 價值低 → 放大排隊痛苦，收益為負（X 貼文的場景）。

## 4.2 範例一：Discord 任務分派（原討論串場景）

**情境**：社群 Discord 伺服器的 bot，收到成員請求後要分派處理（回答 FAQ、排活動、審核貼文、匯出報表）。

| 問題 | 得分 | 理由 |
|---|---|---|
| Q1 分支獨立性 | 1 | 同一伺服器的成員狀態、權限、訊息脈絡是共享的 |
| Q2 可驗收性 | 1 | 回答對錯要查，但可由單一審核步驟處理 |
| Q3 Context 壓力 | 0 | 一個伺服器的日常事件流遠小於 context 上限 |
| Q4 任務價值 | 1 | 例行營運，價值中等 |
| Q5 共享瓶頸 | 0 | Discord API 有嚴格 rate limit，所有 agent 共用 |
| **總分** | **3** | **→ 單代理 + 工具** |

**結論**（呼應你的觀察）：Discord 任務分派**不需要代理群**。正確做法是：單一 agent + 明確的工具集（read_messages、assign_role、create_event、export_report）+ 排隊佇列。開 200 個 agent 只會讓所有分支去搶同一份 Discord API rate limit，正是貼文嘲諷的「附帶限流器的分散式失業模擬器」。

**例外（會升級到主管–工人的形狀）**：「把過去 50 個頻道的討論各整理成一份摘要」——這時 Q1=2（各頻道獨立）、Q3=2（總量超過單一 context）、Q2=2（摘要可獨立驗收），總分足以開 3–5 個 subagent 扇出。

## 4.3 範例二：廣度型研究（對照組）

**情境**：「調查 200 家公司的供應商並比較」。

| 問題 | 得分 |
|---|---|
| Q1 分支獨立（每家公司一組） | 2 |
| Q2 可驗收（每組回傳結構化欄位） | 2 |
| Q3 Context 裝不下（200 家的原始資料） | 2 |
| Q4 價值高（投資/採購決策） | 2 |
| Q5 無強共享瓶頸（公開網路查詢） | 2 |
| **總分** | **10 → 平行扇出** |

這就是 Anthropic 90.2% 提升所處的象限。

## 4.4 上線前的驗證清單

1. **先寫 20 條代表性的測試題**（Anthropic：小型 eval 足以看到改動效果）；
2. **單代理基線先跑分**：沒有基線的多代理demo 不算證據（B1 論文的核心批評）；
3. **對照時控制 token 預算**：允許多代理多花 15× 就要明說，並另外報告「同預算比較」；
4. **記錄三項帳**：總 token、P95 延遲、失敗重試次數；
5. **回頭看分數**：任何一題退步到 0 分就退回單代理。

## 4.5 何時重新評估

- 模型升級後重測（模型越強，多代理相對優勢越小）；
- 任務量級變化（context 壓力、rate limit 政策都會變）；
- 出現新的失敗模式就回到 MAST 的 14 種分類對照。
