核心結論（誠實版）

TL;DR
這題是討論，不是結論

原貼文是徵求案例：作者要的是「單代理絕對做不到、且不是因為單代理沒被給足 token」的可量測案例。截至撰寫時，討論串（67 則回覆）尚未有人交出符合此標準的證據鏈。本站整理的是「現有研究能支持到什麼程度」。

多代理真正贏的條件（要同時成立）

  • 分支真正獨立：不需要即時共享狀態
  • 輸出可低成本匯總、可獨立驗收
  • 資料量超過單一 context，必須分載
  • 任務價值付得起 10–15× token

→ 對應象限：廣度型研究、海量平行資料蒐集（Finance Agent +57~+81%）

單代理贏的形狀

  • 任務有強序列依賴（規劃、長程寫碼）
  • 分支需要共享上下文與狀態
  • 受共享 rate limit 節制（Discord API、單一訂閱額度）
  • 單一 context 裝得下全部工作集

→ 對應象限：Discord 任務分派、SWE-bench、PlanCraft

一句話

多代理不是「更聰明」，是「花更多 token 換更寬的探索」；值不值得，取決於任務的形狀與單價。

為什麼

開 200 個 agent 只會讓所有分支去搶同一份 Discord API rate limit——正是原貼文嘲諷的「附帶限流器的分散式失業模擬器」。在共享瓶頸下，排隊不是缺點，是正確做法。只有當任務變成「50 個頻道各整理一份摘要」這種可獨立扇出的形狀時，才升級成 3–5 個 subagent。
