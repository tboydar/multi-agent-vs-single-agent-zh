§ 03 · DECISION FRAMEWORK

決策框架：五問評分表

討論串吵不出結果的主因，是雙方沒有共同判準。這張表把「協調成本的五個條件」變成可打分的工具——動手點下面的分數，即時得到架構建議。

§ 03A

互動評分表

0–10 POINTS
Q1｜分支獨立性各分支需要即時共享狀態嗎？
Q2｜可驗收性分支輸出能被獨立檢查、低成本匯總嗎？
Q3｜Context 壓力任務資料量會撐爆單一上下文嗎？
Q4｜任務價值產出價值付得起 10–15× token 嗎？
Q5｜共享瓶頸是否受共享 rate limit / 單一狀態源節制？
0 / 10
建議請先點選各題分數
兩條一票否決：① Q1＝0（分支必須同步協作）→ 無論總分一律單代理；② Q5＝0 且 Q4≤1（搶額度且價值低）→ 放大排隊痛苦，收益為負。
總分建議架構說明
0–3單代理 + 工具/工作流先用最簡單的形狀；佇列解決排隊
4–6單代理 + 抽查式平行（best-of-n）同題取樣投票，不做任務分工，規避交接成本
7–8主管–工人（2–4 agents）僅 Q1、Q2 皆滿分時啟用；分支數從小開始
9–10平行扇出（≥5 agents）Q3 也滿分才考慮；先驗證匯總端不是瓶頸
§ 03B

範例一：Discord 任務分派（原討論串場景）

3 / 10

情境：社群 Discord 伺服器的 bot，收到成員請求後分派處理（回答 FAQ、排活動、審核貼文、匯出報表）。這正是「要不要開代理群」的典型爭論點。

評分項得分理由
Q1 分支獨立性1同一伺服器的成員狀態、權限、訊息脈絡是共享的
Q2 可驗收性1回答對錯要查，可由單一審核步驟處理
Q3 Context 壓力0日常事件流遠小於 context 上限
Q4 任務價值1例行營運，價值中等
Q5 共享瓶頸0Discord API 有嚴格 rate limit，所有 agent 共用
總分3 / 10→ 單代理 + 工具 + 佇列
結論

Discord 任務分派不需要代理群。正確做法：單一 agent + 明確工具集（read_messages、assign_role、create_event、export_report）+ 排隊佇列。開 200 個 agent 只會讓所有分支去搶同一份 Discord API rate limit——正是貼文嘲諷的「附帶限流器的分散式失業模擬器」。

例外（升級門檻）：「把過去 50 個頻道的討論各整理成一份摘要」→ Q1＝2、Q3＝2、Q2＝2，總分足以開 3–5 個 subagent 扇出。

§ 03C

範例二：廣度型研究（對照組）

10 / 10

情境：「調查 200 家公司的供應商並比較」。

評分項得分理由
Q1 分支獨立2每家公司一組，互不依賴
Q2 可驗收2每組回傳結構化欄位，機器可合併
Q3 Context2200 家的原始資料超過單一 context
Q4 價值2投資／採購決策，高價值
Q5 瓶頸2公開網路查詢，無強共享瓶頸
總分10 / 10→ 平行扇出（這就是 +90.2% 所處的象限）
§ 03D

上線前的驗證清單

PRE-FLIGHT
  1. 先寫 20 條代表性的測試題（小型 eval 足以看到改動效果）。
  2. 單代理基線先跑分——沒有基線的多代理 demo 不算證據。
  3. 對照時控制 token 預算：允許多代理多花 15× 就要明說，另外報告「同預算比較」。
  4. 記錄三項帳：總 token、P95 延遲、失敗重試次數。
  5. 模型升級、任務量級變化、rate limit 政策調整時重新評分。
