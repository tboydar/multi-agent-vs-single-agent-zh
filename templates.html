範本：三種架構可直接複製

依評分結果選一個形狀。所有 prompt 遵循 Anthropic 的委派原則：給目標、給邊界、給格式、給預算、給完成條件。

範本 A

單代理 + 工具（Discord 任務分派的預設解）

SCORE 0–3
Discord event → 佇列(queue) → [單一 Agent] → tools → 回應

評分依據：Q1=1、Q3=0、Q5=0（見決策框架）。佇列天然解決「多 agent 搶額度」——排隊不是缺點，是共享瓶頸下的正確做法。

System Prompt 範本

你是「伺服器任務代理」，負責一個 Discord 伺服器的日常任務分派與執行。

規則：
1. 一次只處理佇列中的一個任務；處理完成才取下一個。
2. 先判斷任務類型，再選擇對應工具，禁止一次呼叫多個寫入工具：
   - FAQ/問題   → search_kb + reply
   - 活動安排   → read_schedule + create_event
   - 審核       → read_context + moderate（需人工確認的項目一律回報）
   - 報表       → export_report（>30s 的工作改回「已排入背景任務」）
3. 你沒有其他 agent 夥伴；遇到需要多方向調查的任務，
   依〈扇出規則〉請求開 subagent（見範本 C 的門檻）。
4. 所有外部呼叫受同一份 Discord API rate limit 節制：呼叫前先檢查
   冷卻時間，撞到 429 就退避重試，不要平行重試。
5. 輸出一律為 JSON：{task_id, status, tool_calls, result, needs_human}
範本 B

主管–工人（僅在評分 ≥7 時使用）

2–4 AGENTS
queue → [Lead Agent 分派] ─┬─ [Worker 1] ─┐
                              ├─ [Worker 2] ─┼→ [Lead 匯總/驗收] → 回應
                              └─ [Worker 3] ─┘

委派 prompt（教會 orchestrator 如何分派）

【分派格式】每次委派必須給 subagent 以下五欄，缺一不可：
1. Objective   : 單一、明確的目標句（一個分支只准有一個目標）
2. Scope       : 明確邊界（「只調查 X，不包含 Y」——避免分支互相重疊）
3. Output schema: 回傳欄位與格式（讓匯總端可機器合併）
4. Budget      : 最多 N 次工具呼叫 / M token，超過就回傳目前結論
5. Done criteria: 什麼狀態算完成（防止無止境搜尋）

【規模規則】
- 簡單事實查找 → 1 個 agent、3–10 次工具呼叫（不要開分支）
- 一般比較題   → 2–4 個 subagent，各 10–15 次呼叫
- 複雜廣度調查 → 才考慮 >10 個 subagent，且必須先通過五問評分表

匯總端驗收 prompt

你是匯總者。收到各分支回報後：
1. 依 Output schema 合併；
2. 檢查覆蓋率：每個 Objective 是否都有 Done criteria 的證據？缺漏列清單；
3. 有缺漏 → 最多重試 1 輪補查；仍缺 → 標記 needs_human，不要自己編。
4. 回傳：{merged_result, gaps[], token_spend, branches_used}
範本 C

扇出閘門（防呆：一行判斷要不要開多代理）

PYTHON
def should_fan_out(task, ctx) -> dict:
    score = 0
    # Q1: 分支可獨立執行（不需要彼此即時同步）
    score += 2 if task.independent_branches else (1 if task.loose_coupling else 0)
    # Q2: 分支輸出可自動驗收、低成本匯總
    score += 2 if task.auto_verifiable else (1 if task.human_reviewable else 0)
    # Q3: 資料量超過單一 context
    score += 2 if task.exceeds_single_context else (1 if task.near_limit else 0)
    # Q4: 任務價值付得起 10-15x token
    score += 2 if task.value_tier == "high" else (1 if task.value_tier == "mid" else 0)
    # Q5: 無共享 rate limit / 單一狀態源瓶頸
    score += 2 if not task.shared_quota else (1 if task.quota_headroom else 0)

    # 一票否決
    if not task.independent_branches:
        return {"fan_out": False, "reason": "Q1=0: 需同步協作"}
    if task.shared_quota and task.value_tier == "low":
        return {"fan_out": False, "reason": "Q5+Q4: 搶額度且價值低"}

    if score <= 3: return {"fan_out": False, "agents": 1, "score": score}
    if score <= 6: return {"fan_out": False, "mode": "best_of_n", "n": 3, "score": score}
    if score <= 8: return {"fan_out": True, "agents": min(4, task.branch_count), "score": score}
    return {"fan_out": True, "agents": task.branch_count, "score": score}
分支數硬上限

先從 2–4 個開始。Nature 2026 觀察到 3–4 個 agent 以上單分支推理品質開始下滑、通訊量超線性成長；「200 agents」在任何評分下都沒有實證支持。任何 demo 都要附「單代理基線 + 同預算比較」才算數。
